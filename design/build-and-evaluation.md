# G03 build and evaluation foundation

Status: host tooling with original test fixtures. Tessryn kernel boot, native
services, GPU execution and inference remain **unavailable**. A fixture pass
establishes only that this harness observed its marker and expected emulator
exit. The freestanding Rust ELF probe is inspected, never executed.

## Selected development profile

[toolchain.lock.json](../toolchain.lock.json) pins upstream Rust 1.96.0 (including
its exact compiler revision and `x86_64-unknown-none` core archive), QEMU 11.1.2
source, and Python 3.14.6 for CI. The installer verifies archive SHA-256 values
before extraction. Tooling uses the Python standard library; setup requires
Python 3.12 or newer. The selected Python version is the tested profile.
CI also runs the tooling contracts on Python 3.12.13 to cover the minimum
supported minor version, including malformed-input failure reporting.
The lock also pins Ninja 1.13.2 and the QEMU build-only Python wheels: setuptools
80.9.0, wheel 0.45.1 and pip 25.2. QEMU's release archive provides its bundled
Meson source; dependency licenses remain in the downloaded archives/local setup.

The supported **development hosts** are Linux x86-64 and macOS arm64. These are
host tooling profiles, not Tessryn supported platforms. Setup writes downloaded
sources, licenses, dependencies and compiled tools only into ignored
`build/toolchain/`. No imported binaries are committed. QEMU uses TCG software
emulation, so hardware virtualization is unnecessary.

On Ubuntu 24.04, install build prerequisites:

```sh
sudo apt-get update
sudo apt-get install -y build-essential pkg-config libglib2.0-dev ninja-build
```

On macOS arm64, install Xcode command line tools and use Homebrew's `pkg-config`,
`glib` and `ninja`. Their versions and the host's compiler/library environment
can change the external emulator binary; the resulting binary hash is recorded.
The selected Rust compiler, target library and QEMU source are hash-pinned.
This is not a claim of bit-identical QEMU binaries across development hosts.

From a fresh repository checkout:

```sh
python3 tools/setup_toolchain.py --jobs 4
python3 tools/build_fixture.py --out build/fixture-a
python3 tools/build_fixture.py --out build/fixture-b
python3 tools/verify_fixture.py --first build/fixture-a/manifest.json --second build/fixture-b/manifest.json
python3 tools/run_emulator.py --manifest build/fixture-a/manifest.json --qemu build/toolchain/bin/qemu-system-x86_64 --out build/pass
```

Directories for builds and results must be empty/new. Keep previous failures
and choose new names for subsequent runs. `TESSRYN_RUSTC` and `TESSRYN_QEMU` can
select tools that match the setup inventory; version strings alone do not prove
upstream provenance. The builder checks the selected binaries and target library
and compiler runtime libraries against the checksum-bound installation record.
The harness independently checks
the QEMU version and requires its binary hash to match the build manifest.

Exercise a real emulator timeout and verify retained evidence:

```sh
set +e
python3 tools/run_emulator.py --manifest build/fixture-a/manifest.json --qemu build/toolchain/bin/qemu-system-x86_64 --fixture hang --timeout 0.5 --out build/timeout
code=$?
set -e
test "$code" -eq 124
python3 tools/verify_fixture.py --first build/fixture-a/manifest.json --second build/fixture-b/manifest.json --result build/pass/result.json --result build/timeout/result.json
python3 tools/g03/evidence.py validate evidence/fixture-registration.json
python3 tools/g03/evidence.py validate build/pass/result.json
python3 -m unittest discover -s tests -v
python3 tools/validate_design.py
```

## Build artifacts and provenance

`pass.rom` and `hang.rom` are original 64 KiB x86 reset ROM fixtures generated by
[rom.py](../fixtures/rom.py). They contain only a reset jump, debug-port writes
and a halt loop. They use no firmware services or disk. `pass.rom` emits
`TESSRYN_G03_FIXTURE_PASS` and writes `0x10` to QEMU's debug-exit port, yielding
host exit code 33. `hang.rom` deliberately never exits.

[rust-probe.rs](../fixtures/rust-probe.rs) and its
[linker script](../fixtures/rust-probe.ld) validate the proposed compiler,
freestanding target, assembly boundary and ELF layout. The builder invokes
`rustc` directly with the exact flags recorded in the manifest, uses bundled
`rust-lld`, remaps checkout/sysroot paths, and retains DWARF and symbols. It checks
ELF64 x86-64, the entry at 1 MiB, executable/non-writable text, no dynamic loader,
no undefined symbols and nonempty debug sections. This validates debugger inputs;
it does not demonstrate a working kernel debugger, C ABI conformance or runtime.
There are no Cargo dependencies. No device compiler or GPU target is selected.

`manifest.json` records schema version, fixture artifact type, source commit,
dirty flag, source snapshot SHA-256, actual compiler/linker/emulator/Python
versions and binary hashes, exact Rust flags, each artifact's hash/length/role,
binary inspection results, unavailable capabilities, and component provenance.
Provenance includes upstream source, revision/archive hash, licenses, modified
files, notices, build/runtime role and distribution requirements. The snapshot
hash covers sorted Git-tracked and nonignored source filenames, file types,
executable modes, file hashes and symlink destinations; generated outputs are
ignored. A dirty checkout is identified explicitly. Setup extracts verified
archives into fresh source trees instead of trusting mutable extracted caches.
It also rebuilds QEMU in a fresh directory and replaces installed Rust/runtime
and Python dependency trees, so stale build objects or extra modules cannot
silently inherit the pinned archive provenance.

Fresh builds use separate output directories with no incremental state. Verification
checks every artifact against its manifest and requires identical complete
manifests. The three original artifact hashes should also match across tested
hosts; compiler and host tool hashes may differ, so cross-host manifests need
not be identical. No native kernel, service or device artifact is fabricated to
fill a manifest. These profiles remain unavailable until their implementations
and qualification evidence exist.

Unavailable native profiles do not block G03's tooling acceptance. A missing or
incorrect toolchain, provenance record, bounded failure result, evidence format,
or reproducible fixture check does block it. Kernel boot, native-service ABI,
exact GPU targets, model execution and physical performance qualification belong
to their implementation and qualification issues; G03 records their absence.

## Emulator ownership and failure behavior

The host owns the evaluator, registration, input validation, process lifetime,
captured logs and result directory. Candidate bytes are read through a checked
regular-file descriptor, hashed against the manifest, and copied into disposable
scratch. Inputs have a 256 MiB limit. The guest receives only the selected ROM;
the harness exposes no host filesystem share, disk, network, monitor, passthrough
device or DMA authority. Candidate-provided QEMU flags and host commands are not
accepted. The exact guest argv is stored using relative filenames:

```sh
qemu-system-x86_64 -machine pc,accel=tcg -cpu qemu64 -m 16M -smp 1 -nodefaults -no-user-config -display none -monitor none -serial none -nic none -no-reboot -bios pass.rom -debugcon stdio -global isa-debugcon.iobase=0xe9 -global apic.vapic=off -device isa-debug-exit,iobase=0xf4,iosize=0x04
```

Every subprocess has a monotonic deadline and a combined stdout/stderr byte
budget. The version probe uses at most `min(timeout, 5)` seconds, followed by an
emulator deadline of `timeout` seconds. Cleanup adds at most a short termination
grace and reaping budget; this is a per-process bound, not a whole-CLI deadline
including build or input hashing. The process session is terminated and killed
when needed, including descendants whose leader has exited. SIGINT/SIGTERM
cancels an active subprocess and preserves a cancellation result. Output is
retained up to the declared cap, with truncation reported as `log_limit`.
If the host denies session termination or reaping, cleanup still closes pipes
and restores signal handlers; the retained outcome is an explicit failure with
its original execution reason and cleanup error, never a pass.

| Result | CLI exit | Meaning |
| --- | ---: | --- |
| `pass` | 0 | Pass fixture marker and debug-exit status both matched |
| `fail` | 1 | Rejected input, emulator failure, or marker/exit mismatch |
| `unavailable` | 2 | Missing emulator or unselected emulator version |
| `timeout` | 124 | Process or inherited log pipes exceeded the deadline |
| `log_limit` | 125 | Combined output exceeded the budget |
| `cancelled` | 130 | Host cancellation during bounded execution |

`stdout.log`, `stderr.log` and atomically finalized `result.json` retain successful
and rejected runs. Existing result directories are never reused. Setup failures
before a directory can be owned return exit 2; storage failures may prevent a
record and must not be interpreted as a pass. Raw logs are untrusted content:
review them for private data before publication. Fixture logs contain only the
public marker. Result JSON contains no absolute host paths, environment secrets
or private prompts. Harness elapsed time is execution metadata, not an inference
latency or a Tessryn performance sample.

## Independent evaluation authority

For experiments, the operator runs these tools and frozen registration from a
separate trusted checkout. Candidates supply only hashed artifacts; they do not
receive evaluator code, criteria, held-out content, result storage, signing,
enrollment or recovery authority. Check evaluator/registration hashes before and
after execution and retain rejected results. `verify_fixture.py` binds retained
results to the current evaluator, registration, manifest and raw log hashes.
Changing trusted code requires a new evaluation.

The local fixture workflow validates this interface, but a mutable checkout and
a host QEMU process do not constitute a qualified hostile-candidate sandbox.
Emulator vulnerabilities, evaluator enrollment, promotion, protected host storage
and recovery enforcement remain RSI01 work. CI uses read-only repository token
permissions and fixed emulator arguments; no privileged job or deployment is
performed.

## Evidence and CI

[Evaluation evidence](evaluation-evidence.md) defines assumptions,
implementation results, preregistration and future measured-performance records.
[Fixture registration](../evidence/fixture-registration.json) explicitly marks
numerical, held-out and performance evidence unavailable. The
[performance template](../evidence/performance-template.json) is an unfilled
assumption, not a preregistration or measurement.

[G03 CI](../.github/workflows/g03.yml) runs unit failure/cancellation tests,
design validation, checksum-pinned setup, two independent builds, a QEMU fixture
pass, a QEMU timeout and retained-evidence verification. It uploads only manifests
and controlled fixture logs/results for 14 days, including on failure; downloaded
tools and third-party binaries are not published. Actions are pinned to commits.
